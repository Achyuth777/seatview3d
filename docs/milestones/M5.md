# M5 Admin

## What changed

- **Own entry point:** `admin.html` loads `src/admin/` as a separate bundle (5.4 KB gzipped), with its own sign-in screen, header and section navigation (Feeds, Cinemas, Layouts, Activity, Mail). The public site no longer contains admin code. Fastify and `vercel.json` route `/admin` to it.
- **One identity system:** admins sign in with their normal SeatView account. The server checks the role on every admin read and write, from the database at request time.
- **Two-step sign-in:** RFC 6238 TOTP, with no new dependency. It's required when `ADMIN_MFA_REQUIRED=true`, which is the default when `NODE_ENV=production`. Each session must pass it separately.
- **Nothing sensitive in the browser:** API responses no longer include the user's role, and roles can only be granted from the server's command line. The TOTP secret is shown once, to the admin enrolling.
- **Ownership:** every `/api/me` route works only on the signed-in user's own records, and other accounts can't read them (tested in Vitest).
- **Admin tasks:** correct a venue; add or remove aliases; merge duplicates; fix the provider link (marked as set by an admin, and kept through directory syncs); map an auditorium and verify its layout with a measurement source and date; view feed freshness by city; retry a failed sync; review the audit log; check failed email deliveries.
- **Sync status:** each city shows the last successful sync, the latest failed attempt and the cache expiry as separate facts, with advice on what to do.

## Freshness: polling, and why

Open discovery and cinema pages revalidate every **30 seconds** while the tab is visible, and immediately when the tab regains focus. Responses are `no-store`, so each revalidation sees the database.

Polling suits this hosting. The frontend may be served from a static host such as Vercel, which can't hold the long-lived connections server-sent events need. Per-page cache revalidation also needs a request anyway. Polling every 30 s costs one small JSON request per open tab, and the window is easy to state and test.

**Measured:** the open visitor page showed the admin's correction 30 s after the edit, with no reload, in both runs (desktop and phone).

## First admin: grant and revoke

1. The person creates a normal account in the app and confirms their email.
2. The owner runs this on the server, with the same database settings as the app:

   ```bash
   npm run admin:grant -- person@example.com
   ```

3. The person opens `/admin`, signs in, scans the setup key into an authenticator app, and enters a code.

To revoke, the owner runs `npm run admin:grant -- person@example.com --revoke`. This takes effect on that person's next request. Signing out ends the session at once.

## Journeys tested

Playwright, Chromium, 1440×900 and 390×844, PostgreSQL `seatview_test`, `ADMIN_MFA_REQUIRED=true`. 8 passed.

- A regular user sees "No admin access", and the server returns 403 for overview, correction, refresh and provider-link changes.
- Admin sign-in with real TOTP setup; the separate layout and sections; a correction reaching an open visitor page in 30 s without a reload; the audit log naming the admin; a provider-link fix; layout verification with source and date.
- **Failure: provider outage.** The failed sync shows in red with its own timestamp, and the retry succeeds. The last success and latest failure are both shown, and the cinema correction survives the import.
- Revoking the role leaves the open admin page at "No admin access" on its next action. Signing out returns 401.

**Vitest:** `tests/admin.test.ts` covers the RFC 6238 test vectors, clock drift, the role never sent, ADMIN_ONLY and MFA_REQUIRED on reads and writes, a new session needing MFA, and revoke and sign-out. 123 passed in total, 5 skipped.

## What failed and how it was fixed

1. **Misleading import status.** A failed import showed "import finished." in green, because a generic message overwrote the provider's result. The admin now shows the actual result, in red when it failed.
2. **Phone form overflow.** Long option text widened the layout form past a phone screen. Form fields are now held to the screen width.
3. **Measured date.** It showed as "Fri Nov 20" because PostgreSQL returned a date object. It's now read as text.
4. **Test helper assumptions.** Someone already signed in on the site goes straight to the two-step code, and a session that has passed it goes straight in. The tests now expect both.

## Remaining risks

- There are no TOTP recovery codes. A lost authenticator needs the owner to reset `totp_secret` and `totp_enabled_at` in the database.
- The TOTP secret is stored unencrypted in the database. Encrypting it would need a server key.
